# 2026-05-13

Today we got the live-audio eval pipeline working end to end and learned
something about what we aren't measuring yet.

We started by reviewing the spec manifest. The eval system had five open
workstreams: live-audio sandbox (code written but unvalidated), Mini-spec
3 calibration (not started), and Wave D — BoN and preference pairs
(acknowledged but no spec files). The immediate work was to close
live-audio-sandbox so the rest of the measurement system has real EVI
audio to score.

Before touching code, we reviewed a new spec: the agent design patterns
decomposition. It restructures the CLM webhook into five independent
layers — `LLMTransport`, `CallerMemoryProvider`, `MemoryManager`,
`RehearseAgent`, and `AgentRouter` — with `CLMResponder` as the pure
orchestrator above them. The spec was sound, but it had a conflict with
the Wave D roadmap. Mini-spec 6 introduced a `CoachResponder` protocol
to sit beside `CLMResponder` for the Best-of-N path. With the new
architecture, that's unnecessary — BoN is a branch inside
`CLMResponder.stream_reply()`, not a parallel class. We fixed the
roadmap, added `generate()` to `LLMTransport` for buffered candidate
collection, updated the stale file path reference, and added the agent
design patterns spec to the manifest as a Wave D prerequisite.

Then we pushed the live-audio bug fixes from the previous session: five
changes that together made EVI respond correctly in the eval harness.
Audio was being sent as one large blob — EVI's VAD never fired. Hume
Octave outputs 48kHz but EVI expects 16kHz — the wrong sample rate was
going in. The phase timeout was 60 seconds and the rollout timeout 180,
both too short for a real EVI session. And `HumeEVIAdapter` never yielded
`CoachTurnComplete`, so the customer driver waited the full timeout on
every turn. All five fixes landed on main.

We ran `make eval-voice-rollout-audio` and got all zeros. The table
showed three rollouts, 194 seconds, every score at 0.00. We looked at the
failure directory. The rollouts had actually completed — there were full
transcripts, real EVI conversation, coach and caller going back and forth
for two and a half minutes each. The runner was recording them as errors
because the Hume SDK writes its structured logs to stdout. The worker
contract says stdout is for the JSON result only, but the Hume client
doesn't know that. The parser tried to validate the whole buffer and
failed at the first log line.

The fix was one function: scan stdout backwards for the last line
beginning with `{`. That's the result. Everything above it is log noise.
We cherry-picked the fix to main and reran.

The second run produced real scores. Delivery came in at 0.88 — Gemini
thinks the prosody and pacing are good. Silence timing scored 0.83 and
interruption rate 1.00. But speech rate was 0.00, which means the coach
is speaking outside the 130–170 WPM target band, almost certainly below
it. That matched the product observation from earlier in the session:
the call feels deadpan, words-per-minute are too slow, the handoff isn't
natural.

That observation opened a larger question about what we're measuring and
what we're not. The delivery judge scores the whole conversation
holistically — it can't tell us which turn broke the feel, and we don't
yet know whether its scores track human perception. The speech rate band
is deterministic and confirmed the slow-speed problem directly. But there
was no metric for pitch variance, no measure of whether the coach's
energy matched the emotional weight of the moment, no signal for whether
the caller was opening up or closing down across the call.

We brainstormed a set of signals to close that gap. Some are
deterministic — pitch variance and RMS energy from librosa, speaking rate
variability across turns, turn-length reciprocity, user response latency
as a comfort proxy, user turn length trajectory as an engagement signal,
phase transition gap at intake-to-practice and practice-to-feedback
boundaries. Others are targeted LLM probes — per-turn expressiveness
rather than a holistic session score, a warmth versus competence rating,
a transition naturalness judge over the handoff turns specifically. Each
was tied to a customer outcome and added to the TODO.

The thread through all of it is that the delivery judge scores 0.88 while
the call sounds like a robot. Either the judge is wrong, or it's measuring
something different from what a caller feels. We won't know which until
Mini-spec 3: a listening session where real scores get compared against
human ratings. That calibration pass is the prerequisite for trusting any
of these signals as training targets.

The speech rate number is actionable right now without calibration. It's
deterministic, it confirmed the observed problem, and it's a dial we can
turn at the EVI config level and immediately remeasure.

In the second half of the day we shifted to persona routing. The goal is
to replace the static `PersonaRegistry` with a system that can build and
remember a practice partner from what the caller says.

We started by writing the spec for `PeerStore` — a Honcho-backed layer
that searches for prior personas on return visits, bootstraps new ones on
first encounter, and accumulates observations across sessions via
Dialectic synthesis. The name matters: this is a peer the caller is
practicing with, not a product persona. Naming it `PersonaStore` obscures
that. The spec settled on `PeerStore`.

The soul document concept came out of that work. A bootstrapped persona
needs more than a name and a voice. It needs identity — something that
determines how the character behaves when the script runs out. We wrote a
soul template with six sections: identity, values, communication style,
emotional landscape, relationship to the caller, and edges. The edges
section is where you tell the model what the character will not do.
Without it, the character collapses under pressure.

We also wrote the LiteLLM routing decision into the spec. All text LLM
calls go through a single OpenAI-compatible proxy. Today the proxy routes
to Haiku. When a self-hosted model is ready, one config entry changes and
nothing else does. The three aliases we're using are `routing-agent`,
`soul-generator`, and `audio-judge`. The audio judge goes directly to Modal
rather than through the proxy — audio inference is a different interface.

We looked at alternatives to Hume Octave for TTS. The motivation was
cost and offline capability — Octave is a good model but it's a paid API
and it's not something we can run ourselves. We looked at vLLM's TTS
support and found it sparse. The real candidate was Moshi's Pocket TTS
from Kyutai Labs. Pocket TTS is a streaming model that runs on a single
GPU and produces natural-sounding speech with prosody control through
description conditioning — similar interface to Octave but self-hosted.
The appeal is that we could run it on Modal the same way we're running
Gemma for eval judging, at near-zero cost when idle. We didn't implement
it today, but it's noted in the spec as the target for the audio pipeline
when we move off Hume.

The vLLM path for audio judging is more mature than we expected. Gemma 4
26B-A4B accepts audio natively via vLLM's multimodal input. We had
already deployed it on Modal for gender eval. The spec formalizes it
as the standard audio judge path with an `audio-judge` LiteLLM alias
pointing at the Modal endpoint.

We also wrote four other specs today. `SurveyAgent` adds a SURVEY phase
after feedback — a conversational 2–3 question probe generated from the
session's eval dimensions, replacing the flat OutcomeProbe binary. The
survey result becomes a training signal at the dimension level, not just
one bit. `VADTurnSegmentation` describes the offline pipeline for slicing
session WAVs into per-turn clips aligned with transcript text — the input
to fine-tuning. `AudioSourceSeparation` takes those clips through
enhancement to 24kHz clean audio with DNSMOS quality filtering.
`PipelineEventBus` decouples session finalization from the audio processing
pipeline using a file-backed outbox — no scheduler, no external queue.

The four pipeline specs are sequential. Session finalization writes an
event. The VAD step reads it and produces clips. Enhancement reads clips
and produces clean audio. The bus just holds the handoffs. We wrote them
as separate specs because the components have different deployment
timelines and different owners when the team grows.

We also caught two bugs in the eval runner from an earlier audio run.
The synthetic caller LLM had its message roles inverted — coach turns were
labeled `assistant` and caller turns were labeled `user`, so the model
thought it was the coach and generated coaching language. The other bug
was that `asyncio.gather()` discarded the `CallerResult` return value, so
token counts were always zero in the eval table. Both fixed and merged.

We added `modal` to the project dependencies and confirmed remote function
execution works. We added `rehearse-eval list-runs` to the CLI — it prints
recent runs with per-rollout scores and audio paths, and `--play` opens
the WAV in QuickTime for listening.
